# 요구사항

## 목적

`portal`은 DJ 레슨 운영자가 학생별 학습 흐름과 피드백을 관리하고, 학생이 레슨 준비·과제·연습 기록·질문을 한 공간에서 이어갈 수 있게 하는 운영 포탈이다.

## 범위

포함 범위:

- credentials 로그인과 student/admin 역할 기반 접근 제어
- 학생·관리자 대시보드
- 학생 관리, 커리큘럼, 과제 제출, 타임라인 피드백
- 관리자 출제 과제(믹스셋 링크·글·둘 다)와 정기 과제 회차, 글 피드백
- 공용 가이드(학생마다 Stann이 열어 준 범위만 보임)와 가이드 구간 질문
- 개인 일정, 노트, 디깅 기록을 묶는 통합 캘린더
- 공지사항, 커뮤니티, 1:1 Q&A
- 캘린더 구독 피드
- 관리자가 연결한 Google·iCloud 캘린더와 학생별 양방향 동기화
- Worker 경유 R2 미디어 업로드와 본문 이미지
- 노트·가이드·게시물·Q&A 본문의 실시간 공동 편집(문서별 Durable Object room)
- 학생 본인 계정 삭제와 다른 기기의 잔여 초안 정리
- Cloudflare D1/R2/OpenNext 배포 구조

제외 범위:

- 결제·정산
- 영상·오디오 스트리밍 플랫폼 자체 구현
- 공개 마케팅 사이트
- 다중 조직·강사 tenant 운영

## 사용자와 역할

| 역할 | 설명 | 주요 행동 |
|---|---|---|
| student | DJ 레슨 수강생 | 일정·커리큘럼 확인, 과제 제출, 노트·디깅 기록과 디깅 보드 편집, 가이드 열람·구간 질문, 질문·커뮤니티 참여 |
| admin | 레슨 운영자 | 학생·콘텐츠·일정·과제 출제·피드백·공지·가이드 관리, 외부 캘린더 연결·학생별 매핑 |

## 기능 요구사항

상태는 저장소의 소스와 자동 검증 수준을 반영한다. `구현`은 코드에 해당 동작이 존재함을,
`부분 구현`·`부분 충족`은 동작 또는 검증이 더 필요함을 뜻한다. 배포·기능 활성화 여부는
[운영 상태 확인 기준](./DEPLOYMENT.md#운영-상태-확인-기준)에 따라 대상 환경에서 별도로 확인한다.

| ID | 요구사항 | 검증 기준 | 현재 상태 |
|---|---|---|---|
| FR-001 | 사용자는 credentials로 로그인하고 역할에 맞는 포탈로 이동해야 한다. | 비로그인 사용자는 로그인으로 이동하고 student/admin은 서로의 시작 화면에 진입하지 못한다. | 구현 |
| FR-002 | 학생은 오늘, 워크스페이스, 커뮤니티를 하나의 포탈 셸에서 전환해야 한다. | 오늘 화면이 다음 일정·피드백·Q&A·최근 공지를 요약하고, 세 섹션의 선택 상태가 유지된다. | 구현 |
| FR-003 | 학생의 레슨·일정·노트·디깅·Q&A·과제는 학생 스페이스에 귀속된 통합 학습 기록으로 탐색할 수 있어야 한다. | 캘린더, 일별 목록, 전체 목록과 상세에서 현재 스페이스를 식별하고, 관리자 목록에서는 항목별 학생을 구분하며, `lessons`와 별도 일정 행을 숨기지 않는다. 학생은 직접 만든 포탈 일정을 상세에서 수정·삭제할 수 있고 레슨·외부 일정은 읽기 전용이다. 수정은 학생이 고친 칸만 저장해, 그 사이 Stann이 옮긴 시간이나 동기화된 칸을 덮지 않는다(같은 칸은 나중 저장이 이긴다, 2026-11-14 사용자 결정). | 구현 |
| FR-004 | 학생은 받은 과제와 별도로 링크·글·둘 다로 자유 제출하며(커리큘럼 진도 화면은 정규 커리큘럼이 생길 때까지 숨김) 피드백을 확인해야 한다(2026-10-29 사용자: 과제는 믹스셋만이 아니다). | 완료 토글, 자유 제출(링크 YouTube 영상·Shorts·라이브·SoundCloud 트랙·세트와 글 5,000자 중 하나 이상), 미디어 재생, 피드백 목록이 동작한다. 학생은 피드백이 달리기 전의 본인 자유 제출을 상세에서 고치고, 취소 우선 2단계 확인 뒤 삭제할 수 있다. 글 제출에도 재생 시점 없는 피드백을 남긴다. 관리자는 재생 중인 위치를 피드백 시점으로 바로 가져올 수 있고, 들으면서 시점만 찍어 두었다가(⌥M, 이 기기에 과제별 보관) 고른 시점으로 내용을 나중에 쓸 수 있다(2026-11-02). | 구현 |
| FR-005 | 관리자는 업무함에서 미답변 Q&A, 피드백 대기, 다가오는 레슨을 처리하고 학생별 학습 상태를 관리해야 한다. | 실제 처리 항목을 우선순위대로 제공하고 Q&A·과제 상세, 학생 목록·상세·추가 경로로 연결한다. 커리큘럼 모듈 관리는 숨김 스위치가 켜졌을 때만 보인다. 피드백 대기는 미리보기 5건을 넘어도 펼쳐 볼 수 있고, 학생 상세 과제 탭에서 피드백이 있는 제출도 다시 열 수 있다. 일정 화면에서 선택 학생의 레슨을 예약·시간 변경·삭제할 수 있다. | 구현 |
| FR-006 | 공지·커뮤니티·1:1 Q&A는 작성, 목록, 상세, 답변 또는 댓글 흐름을 제공해야 한다. | 역할별 작성 권한과 소유권 검사를 서버에서 수행하고 성공·실패 상태를 반환한다. Q&A는 전체 기간의 제목·질문·답변 검색과 일치 미리보기를 제공하고 검색·상태·학생 문맥을 상세/작성/휴지통 왕복에 보존한다. | 구현 |
| FR-007 | 캘린더 피드는 본인·관리자 세션 또는 유효한 opaque token으로만 접근할 수 있어야 한다. | 신규 구독 URL에는 계정 ID를 노출하지 않고, 허용 요청만 `.ics`를 반환하며 token 회전 뒤 이전 URL을 거부한다. 관리자는 기존 URL의 발급 시각을 확인하고, 교체로 학생의 기존 구독이 끊긴다는 확인을 거친 뒤에만 회전한다. | 구현 |
| FR-008 | 미디어 업로드는 인증된 본인 업로드 의도에 대해서만 같은 출처의 Worker가 파일을 받아 R2에 저장해야 한다. 노트·커뮤니티 글·Q&A 본문 편집기는 이미지(JPG·PNG·GIF·WebP, 장당 10MB)를 버튼·붙여넣기·끌어 놓기로 넣을 수 있어야 한다. | 허용하지 않은 형식·크기·실제 내용과 다른 이미지는 서버에서 거부한다. 본문 이미지는 저장할 때 그 문서에 연결되어 문서를 볼 수 있는 사람에게만 보이고(노트는 본인과 관리자), 본문에서 빠져도 문서가 영구 삭제되거나 계정이 삭제될 때 함께 지운다. 첨부·오디오는 파일당 95MiB까지다. | 구현 — 대상 환경의 `0014` 필요 |
| FR-009 | 개인 노트는 수정 이력과 휴지통을 제공하고, 재전송·동시 편집·영구 삭제 뒤 늦은 요청에도 일관된 상태를 유지해야 한다. | version 기반 조건부 저장, 불변 revision·operation ledger, 30일 휴지통, 복원·관리자 purge, tombstone 부활 방지를 격리 D1에서 검증한다. | 구현 |
| FR-010 | 커뮤니티 게시물과 1:1 Q&A는 내용·상태 이력과 휴지통을 제공하고, 댓글·답변을 보존한 채 복원할 수 있어야 한다. | 게시물 full-snapshot revision, Q&A append-only event, version 기반 조건부 변경, 30일 휴지통, 관리자 purge와 tombstone 부활 방지를 격리 D1에서 검증한다. 관리자가 휴지통으로 보낸 글은 관리자만 복원하고, 학생 휴지통에는 "Stann이 지움" 표시와 보관 기한만 보인다(2026-11-13 사용자 결정). | 구현 |
| FR-011 | 학생은 현재 비밀번호와 명시적 확인을 거쳐 본인 계정을 삭제할 수 있어야 한다. | profile·credential·문서 원문·서버 초안을 한 transaction에서 제거하고 기존 session을 즉시 거부한다. 현재 기기는 terminal lock 뒤 직접 정리하고, 사전 등록된 다른 기기만 재접속 때 해당 계정의 로컬 데이터를 정리하며, 저장소 차단 시 수동 정리를 안내한다. | 구현 — 운영 활성화는 개인정보 수명주기 gate 확인 |
| FR-012 | 학생은 전용 Google(공개 또는 비공개 Secret 주소) 또는 iCloud 공개 레슨 캘린더를 읽기 전용으로 연결하고 해제할 수 있어야 한다. | iCal 주소를 실제 읽기·파싱한 뒤 암호화 저장하고, 외부 일정은 읽기 전용 레슨으로 학생 통합 캘린더와 관리자의 그 학생 캘린더에 표시한다. Google 비공개 주소는 그 자체가 열쇠라 공개 주소와 같은 암호화 저장·원문 비반환을 적용하고 이름을 "Google 비공개 레슨 캘린더"로 나눈다. URL 원문은 학생·관리자·API 응답에 반환하지 않는다. | 구현 — 대상 환경의 0013·암호화 secret 확인 필요 |
| FR-013 | 학생과 관리자는 노트 목록과 전체 화면 작성 흐름을 분리해 학생 스페이스 문맥에서 기록을 탐색·작성해야 한다. | 학생/관리자 목록은 행 전체가 노트로 이어지는 한 줄 목록(제목·안전한 평문 미리보기·날짜·작성자)과 전체 기간의 제목·본문 검색을 제공하고, 관리자 학생 상세의 노트 탭에서 최근 노트를 바로 열고 작성할 수 있다. 검색어와 학생 대상은 상세·작성·휴지통 왕복 때 유지하며, 캘린더의 노트 추가는 선택 날짜와 안전한 복귀 경로를 가진 전체 화면 작성기로 이동한다. | 구현 |
| FR-014 | 학생과 관리자는 현재 비밀번호를 확인한 뒤 본인 비밀번호를 바꿀 수 있어야 한다. | 현재 비밀번호 불일치·8자 미만·72 byte 초과·확인 불일치·같은 비밀번호를 거부하고 입력을 유지한다. 성공하면 현재 기기 로그인은 새 비밀번호로 다시 발급하고, 비밀번호 지문에 결합된 다른 기기의 기존 로그인은 다음 요청에서 거부한다. 지문 결합 이전에 발급된 로그인은 최대 수명(7일)까지 유지된다. | 구현 |
| FR-015 | 관리자는 비밀번호를 잊은 학생에게 임시 비밀번호를 발급할 수 있어야 한다. | 학생 상세에서 취소 우선 확인 뒤 발급하고 원문은 발급 직후 한 번만 보여 준다. 발급 즉시 학생의 현재 비밀번호와 기존 로그인을 거부한다(지문 결합 이전 로그인은 FR-014의 최대 수명 한계를 따른다). 임시 비밀번호로 로그인한 session은 새 비밀번호 설정 화면과 로그아웃만 쓸 수 있고, 학생이 새 비밀번호를 정하면 일반 로그인으로 다시 발급한다. 관리자는 학생이 아직 바꾸지 않았는지만 확인할 수 있다. | 구현 |
| FR-016 | 관리자는 이름·이메일만으로 학생 계정을 만들고 가입 링크를 전달해야 한다. 가입 링크는 학생 이메일로도 보낸다(2026-11-12 사용자 결정). | 관리자는 학생 비밀번호를 정하지 않는다. 가입 링크는 발급 직후 한 번만 보이고 7일 동안 한 번 쓸 수 있으며, 학생이 링크에서 비밀번호를 정하기 전에는 로그인할 수 없다. 링크 token은 주소의 `#` 뒤에 두어 서버 요청 주소에 남지 않는다. 가입 전 학생은 학생 상세에서 링크를 다시 발급할 수 있고, 다시 발급하면 이전 링크는 쓸 수 없다. | 구현 |

## 문서 수명주기와 개인정보 정책

| 항목 | 확정 정책 | 현재 적용 상태 |
|---|---|---|
| revision 보존 | 개인 노트와 게시물의 full-snapshot revision은 문서가 active이거나 휴지통에 있는 동안 모두 보존한다. Q&A는 질문 상태·삭제 상태의 불변 event와 답변을 보존한다. 과거 이력을 개별 삭제·수정하지 않으며 영구 삭제 또는 승인된 계정 삭제 때 본문과 함께 제거한다. | 개인 노트·게시물·Q&A 적용 |
| 휴지통 | 삭제 시점부터 30일 동안 복원할 수 있다. 30일이 지나도 자동 삭제하지 않으며 관리자만 명시적으로 영구 삭제할 수 있다. 게시물 댓글과 Q&A 답변은 휴지통 이동·복원 동안 함께 보존한다. 복원 후 다시 삭제하면 새 삭제 시각부터 계산한다. | 개인 노트·게시물·Q&A 적용 |
| 영구 삭제 | 관리자, 30일 만료, 현재 version 일치를 모두 요구한다. head와 revision·event·하위 댓글 또는 답변을 제거하고 최소 operation ledger와 tombstone을 남겨 늦은 요청의 부활을 막는다. | 개인 노트·게시물·Q&A 적용 |
| 문서 최대 크기 | sanitize가 끝난 개인 노트 HTML 본문은 800 KiB, 제목은 200자까지 허용한다. Server Action 기본 body에 action/form envelope 여유를 남긴 값이다. 초과 요청은 head·revision·receipt를 쓰지 않고 로컬 초안을 유지한다. | 개인 노트 적용 |
| 사용자 저장공간 | 사용자별 active/trash head와 내용 변경 revision을 합쳐 100 MiB를 허용한다. `TRASH`·`RESTORE_TRASH` 상태 snapshot은 사용자 quota에서 제외하되 실제 DB 사용량에는 포함해 별도 관측한다. 한도 초과 시 내용 저장·과거 revision 복원을 막고 휴지통 이동·영구 삭제는 허용한다. | 개인 노트 적용, 운영 경보 미구현 |
| 서버 초안 | 노트·가이드·게시물 수정은 계정 서버 초안을 쓰지 않고 문서 room이 작업본을 보관한다. 새 게시물·Q&A 질문·답변은 본인의 여러 기기가 같은 draft room(`draft:<종류>:<본인>:<범위>`)을 공유하고, 등록 operationId를 room에 두어 어느 기기에서 등록해도 한 번만 생성되며 성공 뒤 모든 기기의 draft가 비워진다(등록 뒤 다시 고친 내용은 남긴다). 예전 `document_server_drafts`와 기기 로컬 초안은 지우지 않고 새로 쓰지도 않으며, 계정 메뉴의 읽기 전용 "이전 초안 보관함"(`/dashboard/drafts`)에서 복사·삭제만 한다. 서버 초안은 소유자 본인 것만 보인다. 댓글·과제 피드백·자유 제출·플레이리스트 같은 문서 외 form은 기존 로컬 초안을 그대로 쓴다. 관리자의 과제·정기 과제는 만들기와 고치기 모두 로컬 초안을 쓰고, 고치기 초안은 고치기 시작한 version을 함께 두어 그 사이 과제가 바뀌었으면 되살리기만 하고 저장은 막는다. 일정·카테고리·새 학생처럼 한두 칸짜리 form은 로컬 초안·이탈 보호 대상이 아니다. | 노트·가이드·게시물·Q&A 적용 |
| 충돌 처리 | 같은 문서를 동시에 고치면 room(Yjs)이 자동으로 합치고 선택창을 묻지 않는다. 자동 병합으로 밀린 내용은 revision 이력에서 복원한다. 저장은 `VERSION_CONFLICT`를 만나면 head를 다시 읽어 조용히 한 번 더 저장한다. 노트·게시물 저장은 스냅샷의 복원 표지(lifecycle)를 싣고 D1 쓰기와 같은 SQL 문에서 확인해 복원 뒤 옛 저장이 복원을 덮지 못한다(가이드는 room 세대). 이력 복원은 같은 문서의 한 편집으로 적용되고 열린 편집기는 다시 시작하지 않는다. 휴지통 이동은 room을 보존한 채 편집기를 잠그고 되살리면 이어진다. 영구 삭제(노트·게시물)와 가이드 삭제만 room을 비운다. 다시 적용하지 못한 입력과 읽기 강등으로 보내지 못한 입력은 계정별 로컬 복구본으로 이전 초안 보관함에 보인다. | 노트·가이드·게시물·Q&A 적용 |
| 로그아웃·계정 전환 | 로그아웃은 먼저 해당 계정의 서버 초안 폐기(DISCARD) 대기 요청만 최대 3초 보내고(실패·오프라인이어도 계속), 해당 계정의 canonical·recovery·future·legacy 로컬 초안과 서버 재시도 queue를 즉시 지운다. 삭제 신호를 사전 등록한 오프라인 기기는 익명 상태 동기화 뒤 해당 owner 데이터만 정리한다. 공동 편집의 기기 보관(IndexedDB·localStorage)은 owner별 이름으로 분리되어 로그아웃·계정 전환·계정 삭제에서 해당 owner 것만 지우며 삭제 검증에 포함한다. | 로그아웃·계정 전환·삭제 신호 정리 적용 |
| 계정 삭제 | 학생 본인, 현재 비밀번호, persistent 또는 memory-only 기기 digest와 단일 operation을 요구한다. persistent token은 모두 deletion job에 결합하고 memory-only digest는 token quota와 분리된 initiating receipt로 같은 transaction에 기록하며, 실패하면 job과 함께 rollback한다. profile·credential·문서 본문·revision·event·서버 초안은 즉시 제거하고 managed media는 durable outbox로 삭제한다. anti-replay용 raw 계정 식별자는 30일 보존 경계 뒤 alias 수렴 대상이 된다. | 전용 삭제·현재 기기 정리·bounded alias runner 구현, 대상 환경의 schema·flag·예약 실행은 운영 gate로 확인 |

## 향후 결정 사항

- 관리자 출제 과제의 마감을 학생 `오늘`의 할 일에 어디까지 올리고, 읽음 상태·새 응답 표시를 추가할지.
- 디깅 보드와 과제 피드백을 장기적으로 오디오 파형 기반 작업 공간까지 확장할지.
- 알림 채널을 앱 내부, 이메일, 캘린더 중 어디까지 지원할지.
- 캘린더 예약 동기화의 운영 Cron 주기와 Google 변경 알림 주소를 언제 활성화할지(별도 승인).
- production smoke test 계정·fixture와 게시물·계정 영구 삭제 뒤 R2 media retention·고아 객체 정리를 어떻게 운영할지.
- media deletion outbox와 30일 raw-ID erasure의 production Cron 주기, Workers plan, backlog 경보 임계값과 책임자를 확정할지.
